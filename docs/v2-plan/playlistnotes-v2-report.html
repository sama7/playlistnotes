01 · EXECUTIVE DECISION

Rescue the product, not the old implementation

Playlistnotes is viable again if the product owns its accounts, notes, collections, privacy and internal music identifiers. Spotify becomes one source and destination—not the backend or gatekeeper.

ChoosePostgreSQL

Its constraints, joins, transactions, indexing and search fit users, recordings, providers, notes, tags and ordered collections.

SkipMongoDB Atlas

Atlas is useful managed infrastructure, but document storage is not the best primary model for v2's relational domain.

ChoosePlaylistnotes accounts

Use managed email one-time codes and Google sign-in. Do not make Spotify authorization a prerequisite.

ChooseExisting DigitalOcean app host

Reuse the current droplet for the application while traffic is small, with a separate process and environment.

Prefer if affordableManaged PostgreSQL

Move state off the app host for backups, recovery and easier future scaling. Local PostgreSQL remains a valid validation-stage fallback.

After coreLast.fm recent listens

Make “write about what I just heard” the first post-core experiment; do not use Last.fm as canonical identity.

North-star statement: Playlistnotes is a music journal that accepts links and imports from anywhere. Streaming-service integrations are optional.
02 · WHY THE PIVOT

Spotify authentication cannot be the front door

As of August 6, 2026, a Spotify Web API application in Development Mode can authorize at most five allowlisted Spotify users, and the app owner must have Spotify Premium. That limit applies to people connecting Spotify—not to people creating independent Playlistnotes accounts or opening public Spotify links and Embeds.

The easily confused numbers: Spotify raised the maximum to 25 Client IDs per developer account in July 2026. That means 25 app identifiers, not 25 users per app, and every Development Mode app on the account shares one API quota. Splitting users across Client IDs is neither the architecture nor a legitimate business-scaling plan.

A playlist link works—but at the playlist level

Spotify officially supports playlist Embeds, and its public oEmbed endpoint currently returns a title, thumbnail and iframe for a public playlist without a Client ID, secret or user OAuth. Spotify's current oEmbed request reference does not list playlists even though the live endpoint accepts them, so Playlistnotes treats that preview as best-effort and always keeps an “Open in Spotify” fallback. That is enough to preserve the link and let someone write about the playlist as a whole.

It is not enough to enumerate the playlist's tracks. The Embed is an opaque presentation surface, not a data feed. Track-by-track collection import comes from a user-supplied Exportify-compatible or neutral CSV.

Why sites such as Exportify may still work: an existing service may have Extended Quota access or grandfathered users, but its exact Spotify status cannot be inferred from the outside. Its continued operation does not mean the same access is available to a new individual app. Playlistnotes may accept compatible CSV files, but must not call, scrape or depend on Exportify itself.

What changes—and what stays emotionally true

Old dependency

Sign into Spotify, browse a Spotify library, fetch playlist tracks, and identify every user and note through Spotify.

New foundation

Sign into Playlistnotes, capture a recording from a link, CSV or listening history, and store the meaning in Playlistnotes.

What never changed

The product exists to preserve memories, details, observations and personal context attached to music.

This does not abandon Playlistnotes. It removes Spotify as the gatekeeper while preserving Spotify links and playback as optional conveniences. If Extended Quota becomes realistic later, a richer Spotify adapter can be added without replacing Playlistnotes identity or data.
Validation question: After writing one note, do invited users independently return on a later day to write another? That behavior matters more than total imported tracks or launch-day signups.

04 · DAY-ZERO SAFETY

Do not reopen the old API as-is

The current repository's note endpoints accept browser-supplied user identifiers and do not enforce an authenticated owner. Its Spotify authorization code stores and logs access/refresh tokens and reuses a mutable API client across requests. These are product-blocking authorization and isolation problems, not cosmetic technical debt.

Immediate action: keep v1 in maintenance or read-only mode, export the tiny MongoDB database, remove legacy Spotify tokens after approval, remove credential logging, and rotate the Spotify client secret before public invitation.

Server-derived identity

Every private query derives the acting user from the verified session. The browser never chooses the owner.

Private by default

New notes and collections are private. Publishing requires an explicit action and a clear preview.

Negative tests

Every owned resource must prove that User A cannot read, edit or delete User B's data.

Preserve playlist context safely: a note always belongs to a Playlistnotes recording and may optionally reference a Playlistnotes collection item. This keeps v1's “this song in this playlist” meaning without trusting Spotify IDs as ownership. Publishing a collection never publishes private note bodies automatically.

05 · EXECUTION

The 10-working-day rescue sprint

Cut scope before extending the timebox.
Day 0

Safety and baseline

  • Put v1 in maintenance/read-only mode.
  • Export MongoDB with source counts and a checksum; document v1 behavior.
  • Plan credential cleanup and confirm where v2 code will live.
  • Keep legacy-note import post-core unless explicitly promoted.

Exit: legacy data is safe and the implementation location is explicit.

Days 1–2

Foundation

  • Scaffold Next.js + strict TypeScript.
  • Configure PostgreSQL, Prisma, Clerk, Zod, tests and CI.
  • Create the first schema and prove migration from an empty database.

Exit: email/Google auth creates an isolated local user and CI passes.

Days 3–5

Secure track-note vertical slice

  • Paste a Spotify track link without OAuth.
  • Create/resolve an internal recording and external mapping.
  • Create, list, edit and delete a private note.
  • Fall back to user-supplied metadata when oEmbed fails.
  • Prove cross-user access fails and the flow works with no Spotify credentials.

Exit: two test users are isolated and the core note flow works end to end without Spotify Web API access.

Days 6–7

Collections, links and CSV

  • Capture a public Spotify playlist link as a reference/optional Embed with zero inferred items.
  • Parse Exportify-compatible and documented neutral CSV variants.
  • Preserve order and duplicate tracks.
  • Show matched, created, skipped and failed rows.
  • Protect against accidental repeated imports.

Exit: a realistic CSV becomes a correctly ordered private collection snapshot, while a link alone is never mislabeled as an import.

Days 8–9

Sharing, search and product polish

  • Add private/unlisted/public visibility.
  • Create stable note and collection URLs.
  • Add user-scoped note search.
  • Polish responsive, accessible states and the landing page.

Exit: one item can be shared without leaking any private content.

Day 10

Production and invitation

  • Deploy behind nginx with a separate process, environment and database role.
  • Verify TLS, rate limits, monitoring, backup and restore documentation.
  • Instrument a small privacy-safe event set.
  • Invite approximately ten people.

Exit: the production workflow works without Spotify onboarding and later-day return can be observed.

First post-core experiment: feature-flag a Last.fm “recently listened” inbox, then let the user choose a scrobble and write a note. Do not mirror an entire Last.fm library or use its IDs/artwork as the foundation.

08 · DEFINITION OF DONE

The v2 rescue is complete when…

New users sign in without Spotify.
Core acceptance tests pass with no Spotify API credentials or OAuth callback.
A Spotify track link creates an internal recording and private note.
A public playlist link can create a reference/Embed but infers zero track items.
An Exportify CSV creates an ordered collection snapshot.
Every recording has a Playlistnotes UUID and provider mappings.
Server-side ownership protects every private read and mutation.
Private, unlisted and public behavior is tested.
Stable Playlistnotes share links expose only intended fields.
Publishing a collection never implicitly publishes private notes.
CI passes and production has monitoring and verified backups.
Ten people can be invited without Spotify developer onboarding.
Analytics can observe first-note activation and later-day return.
